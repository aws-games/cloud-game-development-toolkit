    Regional Cache Sub-Module¶

    [!WARNING] Experimental. Not production-ready. Exercised in test deployments only. Inputs may change without a migration path. There is no Region failover. Losing the whole write Region blocks durable writes, locks, branch reads and cache misses. A write-tier task outage is narrower. See Failure behavior.

    A Lore server in a second region, for a studio with offices in two places. It has an NVMe cache and no storage of its own: the write region's S3 bucket and DynamoDB tables stay the single source of truth.

    How it works¶

    Write tier (root module) Regional cache (this module)
    Fragments (file content, trees) S3 bucket + DynamoDB index, durable NVMe cache over the write tier (immutable_store.composite.durable.mode = "replicated")
    New content arriving stored, then an immediate push to every replication peer is attempted receives successful pushes; a missed fragment loads from the write tier on the first cache miss
    Uploads (commit) from this office — forwarded to the write tier; the commit returns once it is stored there
    Cache miss S3 the write tier, over QUIC (41340)
    Branch pointers and locks DynamoDB the write region's DynamoDB tables, through its interface endpoint over VPC peering when dynamodb_endpoint_url is set

    Fragments are immutable and content-addressed, so a cache cannot hold a wrong version. An MRSC Global Table preserved compare-and-swap across 40 tested races, but added cross-region latency. Lore's transactional lock calls cannot use MRSC Global Tables. MREC Global Tables allowed acknowledged concurrent pushes to vanish in the same test sweep. This module therefore keeps branch pointers and locks in the write region.

    Usage¶

    module "regional_cache" {
  source    = "terraform-aws-lore//modules/regional-cache"
  providers = { aws = aws.replica }

  name_prefix           = "lore-dev-london"
  environment           = "dev"
  container_image       = var.replica_container_image   # this region's ECR
  allowed_ingress_cidrs = var.replica_office_cidrs
  vpc_cidr              = "10.20.0.0/16"                 # must not overlap the write region

  write_region                  = "us-east-2"
  write_region_vpc_cidr         = "10.10.0.0/16"
  write_tier_replication_cidrs  = module.lore.private_subnet_cidrs  # 41340 access, see below
  write_tier_dns_name           = module.lore.write_tier_dns_name
  write_tier_ca_certificate_pem = module.lore.ca_certificate_pem
  dynamodb_endpoint_url          = module.lore.dynamodb_interface_endpoint_url
  mutable_store_table_name      = module.lore.mutable_store_table_name
  mutable_store_table_arn       = module.lore.mutable_store_table_arn
  locks_table_name              = module.lore.locks_table_name
  locks_table_arn               = module.lore.locks_table_arn
}

    The root module needs the mirror of this: replication_ingress_cidrs = module.regional_cache.private_subnet_cidrs, dynamodb_endpoint_client_cidrs = module.regional_cache.private_subnet_cidrs, replication_peers = [{ address = module.regional_cache.cache_dns_name, locality = "OtherRegion" }] and trusted_ca_pem = module.regional_cache.ca_certificate_pem. The two VPCs must be peered, with routes passed as vpc_peering_routes on both sides, and each side's Cloud Map hosted zone associated with the other VPC. examples/multi-region wires all of it.

    Access control¶

    Port Who reaches it Protected by
    41337 (gRPC/QUIC, clients) this office's clients; the write tier security group; external JWT validation when configured. The published example requires it
    41339 (HTTP) this office's clients security group only
    41340 (replication, QUIC) the write tier; other cache tasks security group only

    Port 41340 is network-protected, not JWT-protected. Lore's internal replication listener checks no JWT. The compute configuration disables client-certificate checks on this listener, so there is no mTLS either. TLS encrypts traffic and lets each tier verify the server it calls, but any host that can reach port 41340 can read and write fragments. Keep its sources narrow:

    • write_tier_replication_cidrs: the write tier's private subnet CIDRs (root output private_subnet_cidrs). Null falls back to the whole write_region_vpc_cidr.
    • On the root module, replication_ingress_cidrs: this cache's private subnet CIDRs (output private_subnet_cidrs), not its VPC CIDR.
    • Never put office, VPN or public ranges on 41340.

    DynamoDB access:

    • Set dynamodb_endpoint_url to the root module's dynamodb_interface_endpoint_url output. The compute task gives it to Lore's mutable-store and lock-store DynamoDB clients through their native dynamodb_endpoint_url settings.
    • The root endpoint has private DNS off and an endpoint-specific TLS name. Its security group admits HTTPS only from this cache's private subnet CIDRs, and its policy names only the mutable store, lock table and lock index.
    • Null keeps the legacy public regional endpoint through this VPC's NAT. The published example does not use that fallback.

    Authentication:

    • auth_mode accepts "none" or "external". For a Cognito write region use "external" with the root module's auth_jwk_endpoint and auth_jwt_issuer outputs.
    • With "external", the plan fails unless auth_jwk_endpoint and auth_jwt_issuer are https:// URLs and auth_jwt_audience has at least one nonempty value.
    • branch_pointer_access = "write_tier" is rejected with authentication enabled. The cache does not forward client tokens to the write tier, so an authenticated write tier would refuse the forwarded branch-pointer calls. Use the default "dynamodb".

    Failure behavior¶

    Measured in test deployments (Lore v0.10.1 unless noted):

    Event Observed
    Cache task replaced New task IP; clients saw "Disconnected" for up to the Cloud Map TTL (10 s)
    Both tiers boot together The cache's DNS name did not exist when the write tier started. With a plain fixed topology the peer was lost until restart; the module now re-resolves peers every replication_peer_refresh_seconds (default 300 s)
    Write-tier ECS task stopped for about 10 minutes, while S3 and DynamoDB stayed healthy (v0.12.0; legacy NAT/public DynamoDB path) London status, sync, history, lock status and a cached 2.5 GB clone worked. Two London content-write commands did not finish within the 120 s harness limit
    branch_pointer_access = "write_tier" lore repository list fails (RemoteMutableStore::list is not implemented); push 0.98 s vs 0.87 s at 55 ms RTT, 2.29 s vs 1.94 s at 136 ms
    MRSC Global Table for branch pointers (locks stayed single-Region) Compare-and-swap held across 40 race rounds, but each office paid cross-Region latency. Lore lock calls use TransactWriteItems, which MRSC Global Tables reject
    Earlier design, storage-layer replication (removed) ~22 s window where far reads failed and content was logged as lost; the reason this module has no storage of its own

    Not measured; expected from the design, and to be verified before production use:

    • Peering link down, write Region healthy: fragment uploads, cache misses and peer pushes over ports 41337/41340 fail. With dynamodb_endpoint_url set, branch-pointer and lock calls fail too because endpoint ENIs sit in the write VPC. The null fallback can still use the public DynamoDB endpoint through NAT, but the published example does not use that path.
    • Whole write Region lost: normal clone, sync, status, commit, push and lock operations cannot finish. Cached fragment bytes may remain on NVMe, but branch pointers and cache misses are unavailable. There is no automatic failover.
    • Cache instance store lost (instance replaced): the cache starts empty and refills from the write tier on demand, so first reads cross Regions.
    • Write-tier push to this cache fails, or happens before the cache name resolves: the commit still succeeds in the write region; the fragment is fetched from the write tier on the first cache miss here.

    Sizing¶

    The cache keeps everything either office commits until it fills, then evicts least recently used content. A cache at least as large as the working set the second office reads keeps nearly every read local. 80 % of the instance store is used by default (94 GB on a c8gd.large).

    Choosing the write region¶

    Put the write tier near the office that commits and pushes the most. From the other office, commits upload to the write region, and push, lore lock and the branch-pointer part of status each make DynamoDB calls in the write region. With dynamodb_endpoint_url, those calls reach private endpoint ENIs over VPC peering. Reads of content that is in the cache never leave the region.

    First apply and restarts¶

    Both sides need the other's DNS record to exist, which it does not when both boot at once; replication peers are re-resolved every replication_peer_refresh_seconds (default 300) on the write tier. After the cache task is replaced it has a new IP; clients may see "Disconnected" for up to the Cloud Map TTL (10 s).

    Branch pointers: DynamoDB or the write tier¶

    branch_pointer_access selects how the cache reaches the write region's branch pointers. The default, "dynamodb", uses the write region's DynamoDB table directly. When dynamodb_endpoint_url is set, the AWS SDK reaches that table through the write VPC's interface endpoint over peering. "write_tier" uses Lore's remote mutable store (what the edge pod uses) to forward each operation to the write tier. Measured from a far-region client with Lore v0.10.1, forwarding was slightly slower (small push 0.98 s vs 0.87 s at 55 ms RTT, 2.29 s vs 1.94 s at 136 ms), and lore repository list fails through it because the remote store does not implement list. Clone, commit, push and sync worked in both modes without authentication. "write_tier" is rejected when auth_mode = "external" until token forwarding is implemented.

    To disable a live interface endpoint, first set this module's dynamodb_endpoint_url to null and deploy the replacement cache task. In a second apply, set the root module's dynamodb_endpoint_client_cidrs to null. This keeps old tasks from using a deleted endpoint.
