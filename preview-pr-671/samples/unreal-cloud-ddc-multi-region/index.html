    Unreal Cloud DDC Multi Region¶

    The Unreal Cloud DDC Multi Region is a comprehensive solution that leverages several AWS services to create a robust and efficient data caching system. It uses a well-designed Virtual Private Cloud (VPC) to ensure network isolation and security. The solution employs an Amazon Elastic Kubernetes Service (EKS) Cluster with Node Groups to manage and orchestrate containerized applications.

    At the heart of the system is an instance of ScyllaDB, a high-performance NoSQL database, running on specially optimized Amazon EC2 instances. The Unreal Cloud Derived Data Cache Container is managed by Helm, a package manager for Kubernetes, and uses Amazon S3 for durable storage.

    Predeployment - Set Up Github Content Repository Credentials¶

    The Unreal Cloud DDC Inter Cluster module utilizes a pull through cache to access the Unreal Cloud DDC image. This requires a secret in Secrets Manager in each region. The secret needs to be prefixed with ecr-pullthroughcache/. Additionally, the secret is required to be in the following format: 

    {
  "username":"GITHUB-USER-NAME-PLACEHOLDER",
  "accessToken":"GITHUB-ACCESS-TOKEN-PLACEHOLDER"
}

    Deployment¶

    Prerequisites¶

    • Terraform >= 1.10.3 and AWS CLI v2, with credentials for the target account
    • A Route53 public hosted zone in the account, for the DDC and monitoring DNS records
    • One GitHub credentials secret per region, as described in Predeployment
    • For the private-endpoint path only: session-manager-plugin and jq

    1. Set your variables¶

    Create terraform.tfvars in this directory:

    regions                         = ["us-west-2", "us-east-2"]
github_credential_arn_region_1  = "arn:aws:secretsmanager:us-west-2:<account>:secret:ecr-pullthroughcache/<name>"
github_credential_arn_region_2  = "arn:aws:secretsmanager:us-east-2:<account>:secret:ecr-pullthroughcache/<name>"
route53_public_hosted_zone_name = "example.com"

    Each GitHub secret must be in the region it is used for. Optional variables:

    Variable Default Purpose
    name_prefix cgd-ddc-mr Prefix for load balancer and DNS names. See Names and DNS records.
    allow_my_ip true Allow your detected public IP to reach the DDC and monitoring load balancers
    eks_public_access true Keep the EKS public API endpoints open. See Reaching the EKS API Without a Public Endpoint.
    eks_public_access_cidrs auto-detected /32 CIDRs allowed on the EKS public endpoints
    ebs_csi_use_pod_identity true EKS Pod Identity (or IRSA) for the EBS CSI driver

    2. Deploy¶

    With the EKS public endpoints open (the default), deploy both regions, with replication enabled, in one command:

    terraform init
terraform apply

    The deployment takes about 30 minutes. Creating the EKS clusters and node groups takes about 20 of those.

    To keep the EKS public endpoints closed, follow Reaching the EKS API Without a Public Endpoint instead.

    3. Verify¶

    terraform output unreal_ddc_url
curl -i http://<name_prefix>-<region>.<zone>/health/live    # expect 200 and "Healthy", for each region

    Then follow Postdeployment to write and read a test object.

    How cross-region replication is wired¶

    Each region's DDC replicator needs a URL for the other region. The sample gives every region a stable DNS name that is known at plan time, so both regions install in a single terraform apply with replication already enabled:

    region 1 replicator -> http://<name_prefix>-<region 2>.<zone> -> Route53 alias -> region 2 DDC NLB
region 2 replicator -> http://<name_prefix>-<region 1>.<zone> -> Route53 alias -> region 1 DDC NLB

    There is one Helm release per region. A replicator may log connection errors for the first few minutes, until the peer region's NLB and DNS record exist.

    The DDC NLBs are internet-facing, so replication traffic reaches the peer region from its NAT gateway public IP. The sample allows each region's NAT gateway IP (/32) on ports 80 and 8080 of the peer's load balancer security group.

    Names and DNS records¶

    name_prefix (default cgd-ddc-mr, at most 11 characters) prefixes every name that must be unique per account and region or per hosted zone. This lets the multi-region sample run next to the single-region sample in the same account.

    Resource Name
    DDC client endpoint (latency-routed across both regions) <name_prefix>.<zone>
    DDC regional endpoint, also the replication peer <name_prefix>-<region>.<zone>
    ScyllaDB monitoring (Grafana) monitoring.<name_prefix>.<zone>
    DDC Network Load Balancer (per region) <name_prefix>-unreal-cloud-ddc
    Monitoring ALB / target group <name_prefix>-monitoring-alb / <name_prefix>-scylla-monitoring-tg

    <zone> is route53_public_hosted_zone_name. The unreal_ddc_url output is the client endpoint.

    EBS CSI driver identity mode (IRSA vs EKS Pod Identity)¶

    The EBS CSI driver in each region needs AWS credentials to manage EBS volumes. The root ebs_csi_use_pod_identity variable (default true) is passed to both intra-cluster modules:

    • EKS Pod Identity (recommended, the default). Uses eks-auth:AssumeRoleForPodIdentity and installs the eks-pod-identity-agent add-on automatically. It also works in accounts whose AWS Organization SCP/RCP denies sts:AssumeRoleWithWebIdentity. Under IRSA that guardrail leaves the ebs-csi-controller pods in CrashLoopBackOff with AccessDenied, and the add-on never becomes ACTIVE, so terraform apply times out.
    • IRSA (legacy). Set ebs_csi_use_pod_identity = false for the classic IAM Roles for Service Accounts path, for example on Fargate or Windows node groups.
    # terraform.tfvars, override only if you need the legacy IRSA path
ebs_csi_use_pod_identity = false

    Reaching the EKS API Without a Public Endpoint¶

    By default each cluster's public API endpoint is open to your auto-detected public IP (/32). If your egress IP is not stable (NAT pool, VPN, CI), either set eks_public_access_cidrs to your egress CIDR(s), or close the public endpoints and reach each cluster's private endpoint through an SSM port-forward tunnel. Each region needs its own tunnel and its own local port.

    1. Deploy the VPCs and infra first so the clusters and their in-VPC SSM nodes exist:
    terraform apply \
  -target=module.unreal_cloud_ddc_vpc_region_1 -target=module.unreal_cloud_ddc_vpc_region_2 \
  -target=module.unreal_cloud_ddc_infra_region_1 -target=module.unreal_cloud_ddc_infra_region_2 \
  -var 'eks_public_access=false'
    1. Start one tunnel per region, each in its own shell, and leave both running for the whole apply (requires awscli v2, session-manager-plugin and jq):
    AWS_REGION=us-west-2 scripts/eks-api-tunnel.sh 9443
AWS_REGION=us-east-2 scripts/eks-api-tunnel.sh 9444

    Use your own regions values. If a region has more than one EKS cluster or SSM instance in the cluster VPC, pass the cluster name as the second argument or set EKS_CLUSTER_NAME / SSM_INSTANCE_ID.

    1. Point the Kubernetes and Helm providers at the tunnels and run the full apply:
    # terraform.tfvars
eks_public_access           = false
eks_api_local_port_region_1 = 9443
eks_api_local_port_region_2 = 9444

# Do not open the DDC NLB / Grafana ALB to your IP. Test DDC from inside the cluster instead.
allow_my_ip = false

    TLS is still validated against the real cluster hostname, so there is no insecure setting and no 0.0.0.0/0 exposure. The tunnels are needed for every Terraform command that talks to the Kubernetes API, including terraform destroy. Leave both port variables unset (null) to connect to the public endpoints directly.

    Expected Deployment Timeline¶

    • Infrastructure (EKS, VPC, ScyllaDB): ~20-25 minutes
    • Helm Charts and Application Deployment: ~5-10 minutes
    • Total: ~30 minutes

    ScyllaDB Datacenter Naming Important Note¶

    ⚠️ Critical: Due to a ScyllaDB parsing issue with strings containing -1, this sample removes the -1 suffix from datacenter names to prevent configuration errors. Other suffixes remain unchanged. Examples: - us-east-1 → us-east (datacenter name) - us-east-2 → us-east-2 (datacenter name) - us-west-1 → us-west (datacenter name) - us-west-2 → us-west-2 (datacenter name) - eu-west-1 → eu-west (datacenter name) - ap-southeast-1 → ap-southeast (datacenter name)

    You can use any AWS regions - this sample automatically handles the conversion in the Helm configuration and SSM documents. When you see datacenter names like us-east, this represents the us-east-1 region.

    Postdeployment¶

    The sample deploys Route53 records you can use to access your Unreal DDC clusters (see Names and DNS records). <unreal_ddc_url> below is the latency-routed client endpoint from the unreal_ddc_url output. Each record points to an NLB, which may take a few more minutes to become fully available after the deployment completes. You can view the provisioning status of the NLBs on the EC2 Load Balancing screen.

    Client access. With allow_my_ip = true, each region's load balancer security group allows the single public IP detected at apply time (/32), on ports 80, 443 and 8080. Two things can make a test request time out even though DDC is healthy:

    • Your egress IP changes. Behind a NAT pool or VPN, requests can leave from an IP other than the one detected at apply time. Find your IPs by running curl checkip.amazonaws.com a few times.
    • Latency routing picks the other region. <unreal_ddc_url> sends you to the closer region, which may not allow your IP.

    To test one region directly, use its regional name, for example:

    curl -i http://<name_prefix>-<region>.<zone>/health/live

    The Unreal Cloud DDC module creates a Service Account and valid bearer token for testing. This bearer token is stored in AWS Secrets Manager and is replicated to your second AWS region. The ARN of this secret is provided as a Terraform output ("unreal_cloud_ddc_bearer_token_arn") on the console following deployment. To fetch the bearer token you can use the aws CLI: 

    aws secretsmanager get-secret-value --secret-id <"unreal_cloud_ddc_bearer_token_arn">

    To validate you can put an object you can run: 

    curl http://<unreal_ddc_url>/api/v1/refs/ddc/default/00000000000000000000000000000000000000aa -X PUT --data 'test' -H 'content-type: application/octet-stream' -H 'X-Jupiter-IoHash: 4878CA0425C739FA427F7EDA20FE845F6B2E46BA' -i -H 'Authorization: ServiceAccount <secret-manager-token>'
    After running this you should get a response that looks as the following: 
    HTTP/1.1 200 OK
Server: nginx
Date: Wed, 29 Jan 2025 19:15:05 GMT
Content-Type: application/json; charset=utf-8
Transfer-Encoding: chunked
Connection: keep-alive
Server-Timing: blob.put.FileSystemStore;dur=0.1451;desc="PUT to store: 'FileSystemStore'",blob.put.AmazonS3Store;dur=267.0449;desc="PUT to store: 'AmazonS3Store'",blob.get-metadata.FileSystemStore;dur=0.0406;desc="Blob GET Metadata from: 'FileSystemStore'",ref.finalize;dur=7.1407;desc="Finalizing the ref",ref.put;dur=25.2064;desc="Inserting ref"

{"needs":[]}%

    You can then access the same chunk with the following command: 

    curl http://<unreal_ddc_url>/api/v1/refs/ddc/default/00000000000000000000000000000000000000aa.json -i -H 'Authorization: ServiceAccount <unreal-cloud-ddc-bearer-token-multi-region>'

    The response should look like the following: 

    HTTP/1.1 200 OK
Server: nginx
Date: Wed, 29 Jan 2025 19:16:46 GMT
Content-Type: application/json
Content-Length: 66

{"RawHash":"4878ca0425c739fa427f7eda20fe845f6b2e46ba","RawSize":4}%
    For a more comprehensive test of your deployment, we recommend using the bench marking tools. To do so we used a x2idn.32xlarge as it matched Epic's benchmarking instance to test their configuration.

    With the benchmarking tools we ran the following command after compiling the docker image: 

    docker run --network host jupiter_benchmark --seed --seed-remote --host http://<unreal_ddc_url> --namespace ddc \
--header="Authorization: ServiceAccount <unreal-cloud-ddc-bearer-token-multi-region>" all
    Just a note here, you will have to specify the namespace to be DDC as the token only has access to that namespace.

    It is recommended that if you are using this in a production capacity you change the authentication mode from Service Account to Bearer and use an IDP to authenticate and TLS termination.

    This sample also deploys a ScyllaDB monitoring stack, enabling real-time insights into the status and performance of your ScyllaDB nodes. The monitoring stack includes Prometheus for metrics collection, Alertmanager for handling alerts, and Grafana for visualization. You can access the Grafana dashboard by using the "monitoring_url" provided in the sample outputs. To learn more about the ScyllaDB monitoring stack, refer to the ScyllaDB Monitoring Stack Documentation.

    Troubleshooting¶

    Quick Health Checks¶

    Execute these commands from your local machine with AWS CLI and kubectl configured.

    0. Configure kubectl for EKS (Required First)¶

    # Run on your local machine with AWS CLI access
# Update kubeconfig to connect to your EKS cluster
aws eks update-kubeconfig --region <your-region> --name <cluster-name>

# Example for us-east-1:
# aws eks update-kubeconfig --region us-east-1 --name unreal-cloud-ddc-cluster

    1. Check Pod Status¶

    # Run on your local machine
# View all pods in the unreal-cloud-ddc namespace
kubectl get pods -n unreal-cloud-ddc

# Expected: All pods should be in "Running" status
# If pods are in CrashLoopBackOff or Error state, proceed to log analysis

    2. Check Pod Logs¶

    # Run on your local machine
# Check logs for application pods
kubectl logs -n unreal-cloud-ddc -l app.kubernetes.io/name=unreal-cloud-ddc --tail=50

# Check logs for worker pods
kubectl logs -n unreal-cloud-ddc -l app.kubernetes.io/name=unreal-cloud-ddc-worker --tail=50

    3. Verify ScyllaDB Datacenter Configuration¶

    # Run on your local machine
# Get a pod name
POD_NAME=$(kubectl get pods -n unreal-cloud-ddc -l app.kubernetes.io/name=unreal-cloud-ddc -o jsonpath='{.items[0].metadata.name}')

# Check ScyllaDB datacenters from within the application pod
kubectl exec -n unreal-cloud-ddc $POD_NAME -- cqlsh -e "SELECT data_center FROM system.local UNION SELECT data_center FROM system.peers;"

# Expected output should show converted datacenter names (e.g., 'us-east' instead of 'us-east-1')

    4. Check Application Configuration¶

    # Run on your local machine
# View the ConfigMap to verify datacenter names in application config
kubectl get configmap -n unreal-cloud-ddc -o yaml | grep -A 10 -B 5 "KeyspaceReplicationStrategy"

# Verify the datacenter names match what ScyllaDB reports

    5. Direct ScyllaDB Access (Alternative Method)¶

    # Run on one of the ScyllaDB EC2 instances (if needed for deeper troubleshooting)
# SSH to ScyllaDB instance first, then:
cqlsh -e "SELECT data_center FROM system.local UNION SELECT data_center FROM system.peers;"
cqlsh -e "DESCRIBE KEYSPACE jupiter;"

    Common Issues and Solutions¶

    Issue: Pods in CrashLoopBackOff with ScyllaDB Connection Errors¶

    Symptoms: - Pods show CrashLoopBackOff status - Logs contain "Unrecognized strategy option {us-east-1}" or similar datacenter name errors - HTTP 502 errors on health checks

    Root Cause: Datacenter name mismatch between application configuration and actual ScyllaDB datacenters

    Solution: 1. Verify ScyllaDB datacenter names using the commands above 2. Check if region conversion logic is working correctly in main.tf 3. Ensure Helm configuration uses replace(var.regions[X], "-1", "") for datacenter names

    Issue: Terraform Apply Timeout on the DDC Helm Release¶

    Symptoms: - terraform apply waits on helm_release.unreal_cloud_ddc_initialization and fails after 15 minutes (unreal_cloud_ddc_helm_timeout on the intra-cluster module, default 900 seconds)

    Root Cause: Helm waits until the pods are ready and the Service has a load balancer address. A timeout usually means the pods can't start, or the NLB can't be created.

    Solution: 1. Check pod status and logs using the commands above 2. Check the Service events: kubectl -n unreal-cloud-ddc get events --field-selector involvedObject.kind=Service. DuplicateLoadBalancerName means another deployment in the same account and region already uses <name_prefix>-unreal-cloud-ddc. Set a different name_prefix. 3. Verify ScyllaDB connectivity and datacenter configuration

    Issue: SSM Document Execution Failures¶

    Symptoms: - SSM association shows failed status - ScyllaDB keyspace replication not configured correctly

    Root Cause: SSM document using incorrect datacenter names in CQL commands

    Solution: 1. Check SSM document content for correct datacenter names 2. Verify SSM association targets the correct ScyllaDB instance 3. Manually run CQL commands to verify datacenter names

    Monitoring During Deployment¶

    Watch Pod Deployment Progress¶

    # Run on your local machine during terraform apply
# Monitor pods in real-time
watch kubectl get pods -n unreal-cloud-ddc

    Check Helm Release Status¶

    # Run on your local machine with Helm installed
# List Helm releases
helm list -n unreal-cloud-ddc

# Get detailed status of a specific release
helm status unreal-cloud-ddc-initialize -n unreal-cloud-ddc

    Monitor Load Balancer Provisioning¶

    # Run on your local machine
# Check service status
kubectl get svc -n unreal-cloud-ddc

# Get load balancer details
kubectl describe svc -n unreal-cloud-ddc

    Performance Validation¶

    After successful deployment, validate performance using the benchmarking tools:

    # Run comprehensive benchmark
docker run --network host jupiter_benchmark --seed --seed-remote --host http://<unreal_ddc_url> --namespace ddc \
--header="Authorization: ServiceAccount <unreal-cloud-ddc-bearer-token-multi-region>" all

    API Testing¶

    Get Bearer Token¶

    # Get the bearer token from Secrets Manager
TOKEN=$(aws secretsmanager get-secret-value --secret-id unreal-cloud-ddc-bearer-token-multi-region --query SecretString --output text)
echo $TOKEN

    Test API Endpoints¶

    # Test PUT operation (upload data)
curl http://<unreal_ddc_url>/api/v1/refs/ddc/default/00000000000000000000000000000000000000aa \
  -X PUT --data 'test' \
  -H 'content-type: application/octet-stream' \
  -H 'X-Jupiter-IoHash: 4878CA0425C739FA427F7EDA20FE845F6B2E46BA' \
  -H "Authorization: ServiceAccount $TOKEN" \
  -i

# Expected response: HTTP/1.1 200 OK with {"needs":[]}

# Test GET operation (retrieve data)
curl http://<unreal_ddc_url>/api/v1/refs/ddc/default/00000000000000000000000000000000000000aa.json \
  -H "Authorization: ServiceAccount $TOKEN" \
  -i

# Expected response: HTTP/1.1 200 OK with JSON containing RawHash and RawSize

    Note: Replace <unreal_ddc_url> with the unreal_ddc_url Terraform output, or a regional name such as <name_prefix>-<region>.<zone> to test one region. For single-region deployments, use secret name unreal-cloud-ddc-bearer-token instead.

    Deletion¶

    For the cleanest deletion, it is best to first do a targeted destroy for the module.unreal_cloud_ddc_intra_cluster_region_1 and module.unreal_cloud_ddc_intra_cluster_region_2. 

    terraform destroy -target module.unreal_cloud_ddc_intra_cluster_region_1 -target module.unreal_cloud_ddc_intra_cluster_region_2
    Note: If the previous command fails the first time with an error for context deadline exceeded, run the command again.

    Once the resources are successfully destroyed, you can do a full destroy. 

    terraform destroy
